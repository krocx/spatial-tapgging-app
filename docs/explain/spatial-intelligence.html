Spatial Intelligence

the three questions a camera cannot answer alone, and the four layers that answer them
Proprietary & Confidential · Applied Materials

A phone or a headset sees pixels. To put an instruction on the right bolt, SIB has to know where the device is, what it is looking at, and how the work is going. The device is a sensor; SIB is the judge. Any client that sends the same small observations gets the same intelligence back, which is why the iPad, a headset browser and a pair of glasses behave the same.

1 · Where

Frames: the origin

Every pin, tag and panel is stored relative to one origin per chamber. Three ways to find it, in a fixed order of trust, each checking the next.

priorityobject › sealed map › live QR
printed QRthe chamber's identity and the fallback frame · pose + marker size · also carries the chamber's key to the device, never to the server record
sealed world mapan author walked the room once; ARKit relocalises into that feature cloud · origin = sealed pose · QR only checked for drift
scanned objectthe chamber's own shape (sparse point cloud, not a mesh, not a photo) · frame from calibration · survives a moved chamber · re-aligns with Undo
demo tapno chamber in the room: the whole scene lands where you tap, turned to face you · marked demo, never a run
drift checksealed pose vs live QR: more than 5 cm or 10° → "QR moved? using the sealed map" · logged on the run, never silent
settlingafter a lock the pins wait for the origin anchor to converge (≤ 8 s) so they spawn on the final fit, not the first guess
accuracy, measuredAnchor Lab: rigs and runs that end in millimetres - rendered vs physical, per origin kind · numbers only
one frame, three readingsiPad · headset · glasses see the same origina demo never saves a position
2 · What

Perception: references and verdicts

An author shows the system what good looks like at each tag; later a live frame is scored against it. Layered on purpose: SIB does the generic part, the device does what needs its sensors.

splitserver: image · device: Vision + LiDAR
references (training)single photo, or a Cone sweep (14-19 images across a dome + LiDAR depth) · encrypted with the chamber's key before they are stored
server scoreSSIM + colour histogram - the only scoring SIB does itself; it never sees a feature print or a depth map, only JPEGs
device scoreApple Vision feature prints, distance to the nearest reference · cone alignment from camera angle · 60 % image / 40 % depth when depth was trained
by check typepart check: a centre-crop print is authoritative (can flip the verdict) · language check: live OCR matched word by word · others: generic
per-tag thresholdnot one global cut-off: each tag's bar comes from the spread of its own references (max pairwise distance × 2.5, floor 0.8)
readiness before a runa chamber whose tags are not all trained shows the operator an orange or red banner before the inspection starts
verdict, recorded honestlypass · fail · a fail the operator chose to proceed past is stored as overridden, not hidden
what good looks like, per taga verdict anyone can re-checkno model trained on faces or people
3 · How

Contextual intelligence: normal, deviation, hint

Nothing is scripted. What "normal" looks like on a step is learned from completed visits; a deviation from it is the signal; a hint is phrased, shown, and then judged by what happened next.

loopobserve → baseline → signal → hint → score → retire
observationsattention (target · assembly · pin · panel · away) · distance and aim error to the step's part · aligned to the viewpoint · moving · taps (right / wrong part) · replays
baseline per stepfrom completed visits: dwell p50 / p90, on-target ratio p10, wrong-part taps p90 · one session is a baseline; it sharpens with use
signalsdwell · attention-off · wrong-part · look-away · validate-retry · fire only when this visit crosses the step's own percentiles; floors stop a two-visit baseline firing on noise
the hintquotes the baseline and the part's real name · "Show me" spotlights the right parts · muteable per step, per guide, per device · human coach hints are never muted
effectivenesseach hint scored by what followed: completed sooner · no more wrong taps · attention back on target · reached the viewpoint · passed · rolled over the last 50 visits
retirementshown ≥ 5 with effectiveness < 0.3 → retired on that step · mute rate ≥ 0.5 → retired (people said no) · lifts by itself when newer visits score better
heat and notes for authorsper step: a 0-100 heat from left / failed / wrong part / stalled / attention off · plain-language notes only when ≥ 3 visits stand behind them
learned, not configuredsame JSON from any clientglasses as a sensor: same contract, G2 text today
4 · Proof

Evidence: what is kept, what never is

Trust on the floor comes from knowing exactly what a device records. Numbers almost everywhere; images only where a step asks for proof, encrypted, and never from the observation stream.

rulenumbers always · images only on request
the runwho (named shift), which chamber, which guide · per step: time, hints shown or muted, validation result, evidence yes / no · drift · demo flag
evidence photooptional, one per step, taken on purpose by the person · part of the sign-off · stored for the record, not for training
accuracy runsAnchor Lab marks: rendered-vs-physical error in millimetres, per tag, per origin kind · numbers only
presencewho is on which step right now, for a colleague's coaching message · session-scoped, gone when the run ends
neverno images in the observation stream · no free text from the device · no identity beyond the live session · no faces · training references encrypted with the chamber's key · the server never holds that key · a demo placement never counts as a run or lifts a verdict
reads: Analytics · Intelligence · Scorecardexportable, small, durablenothing leaves the site
Why three readings of one frameA printed code can be moved, a room can be rearranged, a chamber can be wheeled out. Each origin kind fails differently, so each checks the next: the object re-bases the map, the map checks the QR, the QR is always there. The pin stays where the author put it.
Why the device scores tooSIB keeps the generic comparison so every client gets a verdict; the device adds what needs its sensors (feature prints, depth, OCR) so the verdict is sharper where the hardware allows. A pair of glasses without LiDAR still gets a verdict - a plainer one.
Why hints retireA hint that does not change what happens next is noise, and noise is muted. Scoring every hint by its consequence, and retiring the ones that fail, is how guidance gets quieter and better with use rather than louder.
